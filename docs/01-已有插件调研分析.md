# 长期记忆插件调研：三个已有 DSH 插件的优缺点分析

> 调研日期：2026-11-01
> 调研对象：
> 1. [dsh-memos-bridge](https://github.com/Swd146296/dsh-memos-bridge)（v0.1.0）
> 2. [dsh-memory-evolve](https://github.com/csyangwen/dsh-memory-evolve)（dshplugins.com 已收录）
> 3. [dsh-memory-graph](https://github.com/zmh2000829/dsh-memory-graph)（v0.7.0）
>
> 本文档也是后续「agent 选修课授课素材」的第 1 章。

---

## 0. 一句话定位

| 插件 | 一句话定位 | 代码规模 | 技术路线 |
| --- | --- | --- | --- |
| dsh-memos-bridge | 把重量级记忆引擎 MemOS「桥接」进 DSH 的配置层组合包 | ~200 行 JS + 4 个 Python 脚本 | MCP stdio + 外部 Python 服务（Neo4j + Qdrant + LLM/Embedding 网关） |
| dsh-memory-evolve | 「纯插件」实现的全能工作台：五轨记忆 + 待办 + 技能 + 多智能体调度 | ~50,000 行 JS（lib/ 30 模块） | 零运行时依赖，纯文本 Markdown 文件（Hermes 风格 `§` 分隔），系统提示词快照注入 |
| dsh-memory-graph | 本地优先的时态知识图谱记忆：自动召回 + 自动总结 + 混合排序 | ~2,800 行核心 TS | SQLite（node:sqlite）+ FTS5 trigram + 可选 embedding + 图谱 + agent/pre-step 挂钩 |

三者的关系很有意思：**一个借外力（MemOS）、一个拼内功（自己写全套）、一个走中道（纯本地、聚焦记忆一件事）**。这正是"各家之长"最典型的三种路线。

---

## 1. dsh-memos-bridge —— 借外力

### 1.1 它做了什么

- 自己几乎不写代码：`index.js` 只有 38 行，只提供一个 `memosBridge` 服务（venv 的 python 路径、runner 路径、工作目录）。
- 通过 `cordis.patch.yml` 插入 DSH 自带的 `@deepseek-ai/dsh-mcp-client` 插件行，用 stdio 拉起一个 Python MCP server（MemOS 的 `mcp_serve`）。
- 附带 4 个脚本：runner 预检（Neo4j 硬依赖快速失败、LLM/embedding 网关软依赖告警）、MemOS 源码补丁（stdout 污染、dotenv override、本地 tokenizer 等 5 处幂等补丁）、venv 安装脚本、冒烟测试。
- Agent 获得 16 个 `mcp__memos__*` 工具：add/search/get/update/delete memory、create/share cube、chat、调度器控制等。

### 1.2 优点

1. **记忆引擎最强**：MemOS 是研究级系统（MemTensor 团队），Neo4j 图记忆 + Qdrant 向量检索 + LLM 摘要分层，语义检索质量是三个插件里天花板。
2. **工程细节讲究**：即便只是"配置层组合包"，也做了 Neo4j 预检快速失败 + 100000 次重连（栈晚起也能自动恢复、免重启 GUI）、stdout/stderr 分离防 MCP 流污染、宿主机端点覆盖。
3. **插件本体零负担**：不复制引擎代码，MemOS 升级即插件升级。

### 1.3 缺点

1. **部署门槛极高**：Docker 栈（Neo4j + Qdrant + MemOS API）+ Python venv + LLM/Embedding 网关，缺一环就废。普通个人用户几乎装不起来。
2. **脆弱性**：补丁脚本锚定 MemoryOS 2.0.30 版本，版本一漂移就要人工对照重打补丁。
3. **隐私与成本**：search/chat 依赖远端 LLM + Embedding 网关，所有记忆内容要过网。
4. **无 UI、无自动召回、无画像分析**：纯工具面，什么都不自动；16 个工具塞满模型工具清单。
5. **无确认机制**：AI 写记忆直接落库，用户没有"提议-确认"闸门。
6. **与用户需求匹配度最低**：没有 SOP/偏好/画像的任何领域建模。

### 1.4 对我们的启示

- ✅ 可借鉴：**预检 + 快速失败 + 自动重连**的健壮性思想；**stdout 是协议通道、日志走 stderr** 的教训。
- ❌ 不可借鉴：外部重服务架构与"零门槛、纯本地"的目标冲突。

## 2. dsh-memory-evolve —— 拼内功

### 2.1 它做了什么

- **五轨记忆**（全部纯文本 Markdown，`\n§\n` 分隔条目，Hermes 兼容格式）：
  - `memory`（全局事实，MEMORY.md）——每回合注入快照
  - `user`（用户档案，USER.md）——每回合注入快照
  - `key`（项目关键记忆，projects/&lt;cwd-hash&gt;/KEY.md）——注入快照，支持 git 分支作用域、渐进式披露（摘要/全量）
  - `project`（项目日志，projects/&lt;cwd-hash&gt;/MEMORY.md）——不注入，按需读
  - `daily`（每日日志，daily/YYYY-MM-DD.md）——不注入，按需读
- **核心机制**：
  - 系统提示词快照注入（`ctx.systemPrompt.context`），快照文本按 diff 注入以保前缀缓存；
  - 每回合收尾"写入义务"提示词（模型每轮主动写 daily/project 进展，KEY 走**建议队列**，用户确认后才写入）；
  - 情绪反馈记录（`【反馈】` 行：正/负情绪 + 任务分类 + 原话摘录 ≤20 字）——积累后可让 AI 分析"最近对哪些方面不满意"；
  - 记忆 Tab Web UI（浏览/编辑/归档/确认队列）+ 记忆同步（git 分支跨设备）+ 版本检测更新（git tag）。
- **周边能力**（大而全）：四轨待办 dtodo、技能管理/自我进化、无限画板、COI 调度外部 CLI 代理（kimi/codex/grok/hermes）、会话广播/房间、提示词注入、会话书签、会话评审 Advisor、web/IM 通知、模型配置、会话搜索、工作区冲突协调……

### 2.2 优点

1. **零门槛**：零运行时依赖（node:fs），`dsh plugin add` 即用；数据就是人可读的 Markdown 文件，可直接用编辑器改、用 git 管理。
2. **对"沉淀 SOP/偏好"的工作流打磨最深**：
   - "AI 只提议、你确认"三原则（KEY 轨进确认队列）——正好解决"AI 擅自乱写记忆"的信任问题；
   - git 分支作用域（项目记忆只在该分支注入）——贴合开发场景；
   - 渐进式披露（摘要先注入、按需展开）——控制上下文开销；
   - 归档机制（记忆多了可归档、可转回）。
3. **前缀缓存意识**：快照按渲染文本变化才追加，daily/project 高频变化轨刻意不注入——工程上很成熟。
4. **工程健壮性**：跨进程锁文件、原子写、drift guard（文件被外部改坏时拒写并备份）、i18n、幂等注册保护、大量边界测试（74 个测试文件）。
5. **文档与运营最成熟**：场景化指南、详细说明 110KB、发布 tag 规范、dshplugins.com 收录。

### 2.3 缺点

1. **没有真正的检索**：快照是全量注入的，记忆多了就上下文膨胀；模型靠 `memory list` 手动翻——没有语义检索、没有相关性排序、没有按需召回。这是它相对 memory-graph 最大的硬伤。
2. **依赖模型自律**："每回合写进展"是提示词义务，模型偷懒就丢记忆——作者不得不加"写入看门狗"（连续 N 轮没写就提醒）来兜底，说明这条路线本质不可靠。
3. **代码体量失控**：50K 行、30 个模块，记忆只是其中 1/5；大量模块（COI、画板、评审……）与记忆无关。单用户维护成本高，功能蔓延明显。
4. **无知识图谱/实体关系**；无自动召回；无画像分析（反馈行只算半成品）。
5. **项目目录按 cwd 哈希**：`projects/<hash>/` 对人类不友好，换电脑/换路径即失联（需靠同步机制找补）。

### 2.4 对我们的启示

- ✅ 可借鉴：**五轨分层**（全局事实/用户档案/项目关键/项目日志/每日日志）非常符合用户"开发 + 职业 + 流程 + 英语 + 投资"多领域并存的需求；**确认队列**（AI 提议、用户拍板）；**git 分支作用域**；**归档**；**纯文本可读性**。
- ❌ 不可借鉴：全量注入（应换成按需召回）、依赖模型自律写日志（应换成程序钩子自动采集）、功能蔓延。

## 3. dsh-memory-graph —— 走中道

### 3.1 它做了什么

- **本地 SQLite**（node:sqlite，0600 权限）：memories / entities / memory_entities / relations / FTS5(trigram) / summaries / turn_transcripts / embeddings 等 9 张表。
- **自动召回**：挂在 `agent/pre-step`（step 1）上，取最新用户消息做混合排序检索，Top-N 注入 `<memory_graph_context>`（明确标记"参考数据，不是指令"），严格字符/token 预算。
- **自动总结**：每回合完成后，LLM 从对话中抽取结构化记忆（JSON schema 约束：content/kind/importance/confidence/stableKey/tags/entities/relations），confidence ≥0.65 才入库；原始轮次归档到 SQLite（有界、有保留期），抽取失败可离线重试。
- **记忆类型**：`preference / fact / decision / constraint / lesson / event / summary` —— 正好覆盖"偏好、SOP、最优操作"。
- **时态图谱**：实体合并/重命名/删除/孤儿检测/重复候选；稳定事实以 stableKey 换代、保留旧版本可 `memory_revert` 回滚；关系谓词归一化。
- **混合排序**：lexical(FTS5 trigram，中文可用) + semantic(可选 embedding，可降级) + graph(距离) + importance + recency(半衰期) + access(访问强化，自动召回不强化防固化)。
- **健壮性工程**：写失败进 outbox 重放、dead-letter；备份/恢复 JSONL；Web 仪表盘（快照接口 + 随机 token + Host/Origin 校验）；每轮开关（默认/本轮开/本轮关）。
- 18 个工具：remember/recall/graph/forget/expand/archive_*/entity_*/revert/backup……

### 3.2 优点

1. **"跨对话调用"这件事做得最扎实**：自动召回 + 混合排序 + 预算控制，是三个插件里唯一真正解决"记忆怎么按需回到上下文"的。
2. **知识图谱是独有优势**：实体关系、去重合并、孤儿检测、可回滚——记忆库"建错能改、长期可维护"，这对"长期积累"至关重要。
3. **可靠性与安全性工程最好**：outbox、降级（embedding 挂了自动回退词法）、备份、HTTP 安全校验、权限 0600。
4. **代码质量高**：~2,800 行核心 TS、类型齐全、单测 + CI；模块边界清晰（store/summarizer/semantic/outbox/runtime-policy/web-route/budget）。
5. **数据可审计**：每条记忆带来源会话/轮次、总结请求与响应存证。

### 3.3 缺点

1. **AI 全自动写入，无确认闸门**：置信度阈值只是软约束，用户事后才能发现"AI 记了不该记的"——与 memory-evolve 的确认队列正相反。
2. **无多轨组织**：一个 profile 一个库，没有"项目/全局/每日"分层，也没有项目作用域；多项目要换 profile 或换数据库路径。
3. **无跨设备同步**；存储是 SQLite，人类不可直接读（有 JSONL 备份但非日常形态）。
4. **无 SOP/提示词库、无待办、无画像分析**；lesson 类型只能当"经验条目"用，缺少针对"SOP 流程"的结构化支持。
5. **可视化功能**：图谱 UI 已内置，但"看记忆列表/管理记忆"的日常 UI 偏弱（工具驱动为主）。

### 3.4 对我们的启示

- ✅ 可借鉴：**自动召回 + 混合排序 + 预算控制**（核心）；**结构化记忆类型**（preference/decision/lesson 等）；**时态图谱 + 可回滚**；**outbox/降级/备份**；**每轮开关**；**归档重放**。
- ❌ 不可借鉴：全自动写入（应加确认闸门）；单库无分层（应加轨/领域维度）。

## 4. 对比矩阵（按用户需求维度）

| 需求维度 | memos-bridge | memory-evolve | memory-graph | 用户要什么 |
| --- | --- | --- | --- | --- |
| 长期保留、可持久化 | ⭐⭐⭐（引擎强但依赖重） | ⭐⭐⭐⭐（纯文本，git 可同步） | ⭐⭐⭐⭐⭐（SQLite+备份+回滚） | **核心需求** |
| 跨对话自动调用 | ❌ 无（全靠手动工具） | ⭐⭐（全量注入+手动翻） | ⭐⭐⭐⭐⭐（pre-step 自动召回+排序） | **核心需求** |
| 沉淀 SOP/最优操作/偏好 | ❌ | ⭐⭐⭐⭐（确认队列+五轨） | ⭐⭐⭐（结构化 kind 但无确认） | **核心需求** |
| 领域划分（开发/职业/流程/英语/投资） | ❌ | ⭐⭐⭐（项目轨按目录，其余靠 tags 自定） | ⭐⭐（靠 tags） | 重要 |
| 个人画像分析 | ❌ | ⭐⭐（情绪反馈行，手动分析） | ⭐（有统计字段，无分析） | **需求缺口最大** |
| 零门槛安装 | ❌（Docker+venv+网关） | ⭐⭐⭐⭐⭐（一条命令） | ⭐⭐⭐⭐（npm ci+add） | 重要 |
| 数据透明可迁移 | ⭐⭐（在引擎里） | ⭐⭐⭐⭐⭐（Markdown 文件） | ⭐⭐⭐（SQLite+JSONL） | 重要 |
| AI 写入可控性 | ❌ 全自动 | ⭐⭐⭐⭐⭐（提议-确认） | ⭐⭐（置信度软闸） | 重要 |
| 上下文开销控制 | — | ⭐⭐⭐（渐进式披露，但仍全量） | ⭐⭐⭐⭐⭐（预算+排序+预览展开） | 重要 |
| 记忆库可维护性 | ⭐⭐⭐（引擎自带） | ⭐⭐⭐（归档） | ⭐⭐⭐⭐⭐（实体管理+回滚+GC） | 重要 |

## 5. 结论：各家之长是什么、我们的插件长什么样

### 5.1 各家之长（提炼）

1. **从 memos-bridge 学**：健壮性（预检、快速失败、自动恢复）；协议纪律（stdio 纯净）。
2. **从 memory-evolve 学**：**分层记忆轨**（全局/用户档案/项目关键/项目日志/每日）+ **确认队列**（AI 提议、用户拍板）+ git 分支作用域 + 归档 + 纯文本可读 + Web 管理 UI + 版本发布机制。
3. **从 memory-graph 学**：**自动召回 + 混合排序 + 预算控制**（跨对话调用的正解）+ 结构化记忆类型 + 知识图谱 + 回滚/合并/孤儿 GC + outbox/降级/备份 + 每轮开关 + 原始轮次归档。

### 5.2 三个插件共同的缺口（= 我们的机会）

1. **个人画像分析**：三者都没有真正的"从长期记忆反推用户画像、为策略制定提供基础"的能力（用户明确点名）。
2. **领域分类**：用户的工作横跨 5 个领域，三者都没有一等公民的"领域"维度。
3. **确认 + 自动召回的组合**：evolve 有确认没召回，graph 有召回没确认——**没人把两者合起来**。
4. **SOP 的结构化沉淀**：SOP 是"步骤序列"，不是一句话 fact；三者都只有平铺条目，没有流程结构。

### 5.3 我们的初步设计方向（待用户拍板）

- **纯本地、零外部服务**：SQLite（借 memory-graph 的健壮性与可查询性）或纯文本（借 evolve 的透明性）——二选一或混合。
- **分层记忆轨**：全局事实 / 用户档案 / 项目关键（git 分支作用域）/ 日志（每日+项目）。
- **双写入口**：程序钩子自动采集（回合结束摘要，进确认队列）+ 用户/模型显式 `记忆` 工具（SOP 类直接落库或确认）。
- **自动召回**：agent/pre-step 混合排序召回，预算注入，标记为参考数据。
- **领域标签**：开发/职业/流程/英语/投资 作为一等维度参与召回排序。
- **画像分析**：`画像` 工具/命令，按领域聚合偏好、强项、经验、SOP 存量，生成画像报告（可长期演进为策略建议）。
- **发布与授课素材**：README 双语 + 场景指南 + 发版 tag 规范（学 evolve 的运营成熟度）。
