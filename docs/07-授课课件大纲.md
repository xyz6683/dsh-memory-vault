# 「Agent 选修课」授课课件大纲：从调研到发布一个 DSH 插件

> 以 dsh-memory-vault 的真实开发全过程为案例。全部素材就在本仓库 `docs/` 目录。
> 定位：面向「会用 AI 编程、想自己开发 DeepSeek Harness 插件」的 agent 学员（人或 AI 均可作为学员）。

## 课程信息

- **课时**：4 个模块 × 90 分钟（可压缩为一次 3 小时工作坊）
- **成果**：学员跟着做一遍，得到自己的可发布 DSH 插件雏形
- **配套代码**：本仓库（每章对应一次提交：`fa1fda8` = v0.1.0 全量）
- **素材索引**：01 调研分析 · 02 设计方案 · 03 开发日志 · 04 GUI 实测清单 · 05 发布与授课计划 · 06 发布操作手册

## 模块一：调研——站在三家的肩膀上（docs/01）

**学习目标**：掌握「先调研再动手」的方法论；理解三种插件架构路线的取舍。

| 知识点 | 案例 |
| --- | --- |
| 三条路线：借外力（MCP 桥接）/ 拼内功（纯文件插件）/ 走中道（本地 SQLite） | memos-bridge / memory-evolve / memory-graph |
| 对比矩阵怎么画：按用户需求维度打分，而不是按功能清单 | docs/01 §4 |
| 网络受限环境的调研技巧：git clone 失败 → GitHub API tarball | docs/03 踩坑 1 |
| 结论句式：「召回正解在 X，工作流正解在 Y，共同缺口是 Z」 | docs/01 §5 |

**课堂练习**：给学员三个任意 GitHub 插件，10 分钟产出「一句话定位 + 两个优点 + 两个缺点 + 一个可借鉴点」。

**授课金句**：*调研省下的返工是开发里最便宜的返工——我们直接继承了 memory-graph 的 FTS 接线、outbox、Web 安全三件套，躲开了 evolve 的「全量注入膨胀」和「依赖模型自律」两个坑。*

## 模块二：设计——产品决策在代码之前（docs/02）

**学习目标**：需求映射 → 数据模型 → 机制设计 → 里程碑，每一步可评审。

| 知识点 | 案例 |
| --- | --- |
| 三个必须先拍板的产品决策：存储 / 写入控制 / 功能范围（让用户选，别替用户选） | 我们的三问 |
| 需求映射表：用户的一句话需求 → 设计对策 → 借鉴来源 | docs/02 §2 |
| 分层闸门：显式直写 / 自动提炼待确认 / 日志自动写不注入 | docs/02 §5.1 |
| 数据模型：kind × track × domain × steps 四个正交维度 | docs/02 §4 |
| 里程碑验收标准写法：每步可测 | docs/02 §9 |

**课堂练习**：给「个人待办管理插件」写需求映射表和里程碑验收标准。

**授课金句**：*「AI 只提议、你确认」不是功能清单里的一项，而是信任设计本身。*

## 模块三：开发——公开扩展点 + 失败开放（docs/03、docs/04）

**学习目标**：会查 DSH 公开 API；写测试驱动的小步开发；养成「失败开放」工程习惯。

| 知识点 | 案例 |
| --- | --- |
| 只用公开扩展点：`ctx.tools.register` / `agent/pre-step` / `systemPrompt.context` / `webServer.register` / `ctx.slots` | 全部 16 个工具与 UI |
| API 版本漂移怎么排：从 0.1.x 参考代码移植到 0.2.0 的四类坑（消息源 kind / 会话 API / 工具执行 Promise / CallId 改名） | docs/03 M1 踩坑 4 |
| 中文检索：FTS5 trigram + 2 字词 instr 回退（原创改进点） | docs/03 M1 踩坑 3 |
| 失败开放：LLM 提炼失败只告警不阻塞；outbox 重放；语义/网络降级 | docs/03 M2 |
| 端到端测试：真实 cordis Context + 假 LLM 适配器，验证「轮次→提炼→队列→批准→召回」全链路 | tests/extractor.spec.ts |
| 客户端 UI：`__ModuleLoader__` 打包协议 + slots 注册（list 槽要 id、keyed 槽要 key） | docs/03 M3 踩坑 4 |
| 零依赖安装：把 SDK 包全部声明为 peerDependencies，`dsh plugin add` 零下载 | docs/03 M1 踩坑 6 |

**课堂练习**：写一个带 `output.schema` + `render` 的最小工具并跑通 `ctx.tools.execute` 测试。

**授课金句**：*插件的第一原则是「卸载即净」——所有能力通过公开扩展面挂载，随生命周期完整撤销。*

## 模块四：发布与授课（docs/05、docs/06）

**学习目标**：掌握双通道发布策略；学会把自己的开发过程沉淀为可复用课件。

| 知识点 | 案例 |
| --- | --- |
| 双通道：GitHub topic `dsh-plugin` 自动收录（保底）+ dshplugins.com 人工审核（背书） | docs/05 |
| 审核要求的四件事：安装步骤 / 前置与权限 / 平台与限制 / 规范 URL | docs/05 §发布渠道 |
| 发布前清单与 tag 发版流程 | docs/06 §4 |
| 「开发日志 = 课件」：把踩坑记录当授课素材写，而非事后补 | 本仓库 docs/03 |

**结课作业**：任选其一——
1. 给自己开发的插件补一份 dshplugins.com 可过审的 README；
2. 用「调研→设计→日志→发布」四段式，把最近一个项目整理成课件大纲。

---

## 答辩/评分建议

- 调研（20%）：对比矩阵是否按需求维度而非功能清单
- 设计（30%）：三决策是否明确；数据模型正交性；验收标准可测性
- 实现（30%）：测试覆盖；失败开放程度；对版本漂移的处理
- 发布（20%）：README 完整性；topic 与审核材料；课件结构完整性
