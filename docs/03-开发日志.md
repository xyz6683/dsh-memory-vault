## 2026-11-01 · 调研日：三个插件，三条路线

### 做了什么

1. 拉取三个插件源码（注意：直接 `git clone github.com` 会失败，改用 `api.github.com/repos/<owner>/<repo>/tarball` 下载后解压——**网络受限环境下这是个通用技巧**）。
2. 通读各自 README 与核心源码：
   - `dsh-memos-bridge`：38 行 JS 的 bundle，MCP 桥接 MemOS（Neo4j+Qdrant 外部服务）。
   - `dsh-memory-evolve`：5 万行零依赖纯插件，五轨 Markdown 记忆 + 确认队列。
   - `dsh-memory-graph`：2800 行 TS，SQLite 图谱 + `agent/pre-step` 自动召回。
3. 产出《01-已有插件调研分析.md》：对比矩阵 + 各家之长 + 共同缺口。

### 关键结论

- **召回正解**在 memory-graph：`agent/pre-step` 挂钩 + FTS5 trigram（中文可用）+ 图谱距离 + 时间衰减 + 预算注入。
- **工作流正解**在 memory-evolve：分层轨 + 「AI 提议、你确认」+ git 分支作用域 + 纯文本透明。
- **共同缺口**：个人画像分析（用户点名需求）、领域维度、确认+召回的合体。
- 三者都验证了同一件事：**纯插件路线完全可行**，`ctx.tools.register` / `ctx.on('agent/pre-step')` / `ctx.systemPrompt.context` / `ctx.inject(['webServer'])` 是 DSH 0.2.x 的公开扩展面。

### 授课要点（预埋）

- 「先调研再动手」省下的返工：我们直接继承了 memory-graph 的 FTS 接线、outbox、Web 安全三件套，避免了 evolve 的「全量注入膨胀」和「依赖模型自律」两个坑。
- 用户拍板三件事：存储（SQLite+导出）、写入闸门（分层）、范围（聚焦记忆+画像）。**产品决策要在写代码前锁定。**

## 2026-11-02 · M0/M1 骨架与核心闭环（完成 ✅）

### 做了什么

1. **脚手架**：package.json（`dsh.bundle.patch` 清单 + peer 依赖对齐 DSH 0.2.0-rc.2）、tsconfig 三件套、cordis.patch.yml（全量默认配置）。
2. **存储层** `store.ts`（约 1200 行）：schema v1（memories/entities/relations/turn_archives/suggestions/meta + FTS5 trigram 触发器）、稳定事实换代/回滚、确认队列、Markdown 导出、JSONL 备份。
3. **工具面**：`mvault_add / mvault_recall / mvault_expand / mvault_forget / mvault_revert / mvault_graph / mvault_export / mvault_backup / mvault_review`。
4. **自动召回**：`agent/pre-step` 混合排序注入 `<memory_mvault_context>`，标记「参考数据，不是指令」。
5. **领域检测**：查询文本关键词命中 → 领域加权（`domainBoost`）。
6. **验收**：20 个测试全绿（存储/召回/闸门/导出/备份/outbox + 真实 cordis Context 集成测试，验证 pre-step 只注入第一步、工具注册与领域校验）；`dsh plugin add` 安装进本机 web profile 成功（零下载）。

### 踩坑记录（授课素材核心）

1. **git/npm 网络全挂的一天**：`git clone` 被 reset，npm registry 超时。解法：GitHub API tarball + 本地软链 DSH 自带 SDK 包（版本精确一致）+ mmx-cli 里找到 typescript 6.0.3 + 用 node 内置 test runner 替代 vitest——**离线开发闭环**。
2. **不要自己发明 FTS5 接线**：external-content FTS5 + 触发器 + trigram 的接线方式直接沿用 memory-graph（MIT，已在 LICENSE 注明）。
3. **中文 2 字词召回**：trigram 无法匹配 <3 字的词（发版/部署/偏好…），memory-graph 的 `<3 字符` 回退太窄——我们改为「查询中的短词逐个 instr 匹配」的回退，中文查询体验明显更好。
4. **DSH 0.2.0 的 API 漂移**（对照 0.1.x 的 memory-graph 源码开发时必踩）：
   - 消息来源去掉了通用 `plugin` kind，插件须用 `declare module '@deepseek-ai/dsh-llm' { interface MessageSourceMap {...} }` 声明自己的 kind，并带 `form: 'snapshot'`；
   - `CallId` 改名 `ToolCallId`；工具 `execute` 必须返回 `Promise`；
   - `@types/node` 版本不对时 `realpathSync` 会从 `node:fs` 而非 `node:path` 导入。
5. **cordis 的静默陷阱**：插件 `inject` 声明的服务缺失时，cordis **静默延迟装配**（不报错）——测试「配置校验失败会抛错」时必须先备齐全部注入服务，否则断言永远失败。
6. **零依赖安装**：把 schemastery 也放进 peerDependencies，`dsh plugin add` 不需要任何 registry 下载（网络差的环境 526ms 装完）。

### 下一步（M2）

- 轮次归档 + LLM 自动提炼（`llm.stream`）+ 确认队列接通。
- 实体合并/重命名/孤儿 GC。

## 2026-11-02 · M2 自动沉淀（完成 ✅）

### 做了什么

1. **轮次归档**（store.ts）：`turn_archives` 表 + `archiveTurn/turnArchive/markArchive/failedArchives/archiveStatusCounts`，每轮原文有界保留（100K 字符 / 30K token 上限、30 天保留期），提炼失败可离线重试、无需重放对话。
2. **自动提炼**（extractor.ts 新增，约 500 行）：
   - `collectTurnTranscript`：从会话持久事件重建「已完成的轮次」原文（turn/start→turn/end 之间 user/assistant/tool 文本，尾部有界裁剪）；
   - `AutoExtractor`：按会话串行后台队列 + 并发上限 + 指数退避重试（2 次），失败只告警、**绝不阻塞 Agent 回合**；
   - LLM 调用：`ctx.llm.stream` + 严格 JSON schema 校验（`parseExtractedSummary`，字段级白名单），模型输出过不了校验就不进库；
   - **闸门**：候选全部进 `suggestions` 确认队列（`commitExtraction`），用户批准才落 `active`——与 memory-graph 的全自动写入形成对比，与 memory-evolve 的确认队列对齐。
3. **提炼审计**：`extractions` 表存每次提炼的请求/响应原文（session+turn 唯一），任何记忆都能溯源到来源轮次。
4. **确定性领域分配**：候选的 domain 由「该轮用户文本的关键词检测」确定（不信任模型输出），唯一命中才打领域、否则 general。
5. **提炼去重**：候选与 active 记忆、pending 队列做规范化内容比对，重复事实不再骚扰用户。
6. **实体维护工具**：`mvault_entity_merge / rename / find_duplicates / delete / orphans` + `mvault_archive_expand / mvault_archive_retry`（共 16 个工具）。
7. **验收**：26 个测试全绿，含**端到端集成测试**——真实 cordis Context + 真实 DSH 服务 + 假 LLM 适配器：构造完成轮次事件 → 后台提炼 → `mvault_review list` 出现候选 → approve → `mvault_recall` 可召回。

### 踩坑记录（M2 新增）

1. **Node 直跑 TS 的语法边界**：node 的 type-stripping 不支持 `constructor(private readonly ctx)` 参数属性（非可擦除语法）——测试加载直接 SyntaxError。改写成显式字段声明 + 构造函数赋值。
2. **DSH 0.2.0 会话 API 漂移**：`session.events` → `session.snapshotEvents()`；`append()` 对 message 类事件强制第三参 `{ surfaceOp: 'append' }`；`createAssistantMessage` 的 source 不能再写 `kind: 'model'`（kind 由构造器推断，写了反而报 never）。
3. **方法名冲突**：`archive` 一石二鸟（记忆归档 + 轮次归档查询）导致 TS duplicate implementation——重命名为 `turnArchive`，语义清晰。
4. **测试断言要跟实现的校验顺序走**：schema 校验器逐字段报错，测 `importance` 越界前要先补齐 entities/tags/relations 字段。
5. **中文召回测试陷阱**：查询词与记忆内容必须有词面重叠（trigram 是词面匹配，不是语义匹配）——「回答风格」查不到「先给结论再给细节」是正确行为，语义检索留给 M3 的可选 embedding。

## 2026-11-02 · 发布前审查：与宿主内置能力的命名冲突（重要一课）

### 发现

发布前审查中发现：**本会话运行所在的 Harness 平台运行时自带 `vault_*` 工具面**（vault_add / vault_recall / vault_expand / vault_forget / vault_revert / vault_graph / vault_export / vault_backup / vault_review，语义与我们的插件高度重合——同样是「长期记忆的保存/调用/管理」）。而我们的工具恰好也叫 `vault_*`。

虽然用户本机的 dsh `0.2.0-rc.2` 检查代码确认**尚无**内置 vault（全库 grep 无 `vault_add` 字符串），但平台运行时已有——一旦用户升级 dsh、或发布后其他用户在新版本上安装，同名工具注册必然冲突（工具注册表不允许重名，插件 apply 直接失败）。

### 处置

发布前一次性重命名（改名要趁早——工具名是公开 API，发布后再改等于破坏兼容）：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 工具前缀 | `vault_*` | `mvault_*`（17 个工具） |
| 插件 id / name | `memory-vault` | `dsh-memory-vault` |
| 消息源 kind | `memory-vault` | `mvault` |
| Web 路由 | `/memory-vault/snapshot`、`/memory-vault/action` | `/mvault/snapshot`、`/mvault/action` |
| 客户端槽位 id | `memory-vault` | `mvault` |
| 召回块标记 | `<memory_vault_context>` | `<mvault_context>` |

验证：28 测试全绿；构建产物在真实 DSH 服务上下文 boot 通过（17 个 `mvault_*` 工具注册成功）；`--dump-config` 显示新 id 生效。

### 授课要点（这条值得单列一章）

1. **命名冲突检查是发布前必做项**：`grep` 宿主 SDK 与平台运行时，确认工具名/路由/槽位 id/消息源 kind/插件 id 五类命名空间都没有撞车。
2. **evidence > assumption**：不能因为「本机没报错」就假设全生态安全——本机 dsh 版本没有内置 vault，但平台运行时已有，冲突是时间问题。
3. **改名成本曲线**：开发期改 = 一次 sed；发布后改 = 破坏所有用户的工作流。所以「发布前审查清单」要包含命名冲突这一项。
4. 这同时印证了 memory-evolve 的第二条原则「**官方已有的能力不碰**」：宿主的记忆能力正在成为内置面，插件的差异化价值必须是官方没有的部分（我们的领域维度、确认闸门、SOP 结构化、画像分析、Markdown 导出）。
